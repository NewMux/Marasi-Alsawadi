## Operational extension — August 2026

The database now includes additive `sales_ticket_sequences`, `sales_transactions`, `expense_categories`, and `expense_records` tables. The migration was deliberately applied without altering the known nonstandard live reservation fields. Table-existence verification returned all four tables.

Authenticated staff can issue a server-allocated yearly sequential transaction ticket in the format `MAS-YYYY-######`. A ticket is linked to an existing or newly created customer profile, saves the customer visit date and purchase details, and appears in a searchable customer/visit history. The ticket detail has an A4 `@media print` layout and uses the ordinary browser print dialog, which is compatible with regular printers rather than thermal-only hardware.

Only administrators can create, rename, activate/deactivate, or delete expense categories. Managers and administrators can create, correct, and delete dated categorized expenses. New expense records are also reflected in the existing finance ledger; changing or deleting a categorized expense synchronizes its linked finance entry. The revenue-versus-expenses summary intentionally aggregates the new ticket and expense ledgers directly, avoiding duplicate counting from legacy finance entries.

The public no-login demo now has local-only equivalents of the ticket/customer workflow and expense category/expense/report workflow. ## Public ticket, WhatsApp, and gate-entry extension — August 2026

The product-focused ticket desk now creates a cryptographically random public token for every new `sales_transactions` record and returns a customer-facing link at `/ticket/{token}`. The no-login ticket page shows the ticket number, customer name, visit date, paid amount, service, lifecycle status, and a locally rendered QR code suitable for ordinary phone or tablet scanning. It never shows the customer’s phone number or internal staff data.

The cashier can open or copy the ticket link and can send it through the WhatsApp Business Platform only after explicitly confirming that the customer agreed to receive the message. The server uses an approved WhatsApp template, keeps the access token and provider credentials server-side, records queued/sent/delivered/read/failed status, and exposes a signed webhook at `/api/whatsapp/webhook` for Meta status callbacks. Provider credentials are intentionally not fabricated; sending remains disabled until `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, the approved template name, and the production `PUBLIC_APP_URL` are supplied in Coolify.

The new `/gate` route is restricted to `guard`, `manager`, and `admin` roles. The guard page supports camera QR scanning through `html5-qrcode` plus manual or USB-scanner input. A scan is validated server-side against the opaque token, the visit date, payment state, and single-use lifecycle. Allowed scans atomically transition a paid ticket to `checked_in`; repeated, voided, expired, future-date, and unknown tokens are denied and recorded in `ticket_check_ins`. The administrator role selector now includes `Gate guard`.

Database deployment requires applying `drizzle/migrations/0005_add_public_tickets_gate_scans_whatsapp.sql` after the existing ticketing/rate migrations. Existing sales tickets receive deterministic legacy public tokens during the migration. The local test suite now passes with **27 tests**, TypeScript checking passes, and the production build completes successfully. Local browser smoke tests confirmed `/ticket/{token}` renders a safe not-found state without authentication and `/gate` remains behind the sign-in shell.

The remaining production handover items are operational rather than code-completion blockers: apply the new migration to the production MySQL database; configure Meta’s approved template and webhook; provide the final public HTTPS domain; assign real staff accounts to the `guard` role; and run a live pilot with one paid ticket, one WhatsApp delivery, one successful scan, one repeated scan denial, and one unknown-token denial. The public Vercel alias still serves the older demo deployment; the new production path should be deployed through the selected Coolify/Hetzner environment after credentials are entered.

## Quotation-aligned release — 25 August 2026

The current quotation-aligned branch supersedes the older A4/open-access notes above. It restores local username/password authentication, hashed expiring sessions, mandatory first-password change, and real role enforcement. The global system-user shim has been removed.

Commercial Settings is available only to `super_admin`. It manages editable base ticket prices, fixed or percentage fee items, global or selected-price applicability, per-ticket or per-transaction application, expense categories, staff accounts, roles, activation, password resets, and audit activity. The backend rejects all corresponding mutations for staff, manager, admin, guard, and unauthenticated callers.

Cashiers select an active database price and cannot override it. The server reloads the active price and applicable fee definitions, calculates a decimal-safe total, and stores immutable base and fee line snapshots. Receipt output is compact and supports 80 mm by default plus a 58 mm fallback through the normal browser/system print dialog; this is not an A4 print workflow.

Migration `drizzle/migrations/0006_add_super_admin_auth_and_ticket_fee_lines.sql` was rehearsed successfully against a disposable local MariaDB database.
